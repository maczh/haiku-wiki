## Axure .rp 原型无预览图修复（commit 7d5fd72 + 2382afc，IS_PASS: YES）
- 现象：「需求原型」导入 Axure `.rp` 无预览图，卡片空白占位。
- 根因：`.rp` 是专有二进制容器（magic `AC EF 09 00`，JSON 元数据内嵌 JPEG/PNG 截图），**不是 zip**；`buildProjectArchive` 调 `unpackZip` 失败 → 降级 `Degraded=true` 且无 Preview；前端 `PrototypeView.tsx:70` `hasPreview=!!preview && !it.degraded` 因此不渲染。
- 修复：`buildProjectArchive` 非 zip 分支现先 `extractEmbeddedImage`（扫 PNG/JPEG 签名、DecodeConfig 量最长边 ≥120px、挑体积最大张）→ `buildEmbeddedPreview` 落原件 + `imgconv.Convert(imgData,"embedded."+ext)` 派生 preview/thumb（imgconv 不认 .rp 白名单，故用 embedded.jpg 绕过），失败回退原图当预览。
- 标签对齐（2382afc）：内嵌预览 `Kind` 由 `image` 改为 `other`（工程文件），与降级分支及 buildProjectArchive 语义一致；`hasPreview` 与 Kind 无关，预览照常显示。
- 验证：`go build`/`go vet` 0 错误；`go test -run 'Prototype|BuildProjectArchive'` 全绿（含 TestBuildProjectArchiveRealRP 读真实 `/Users/macro/Documents/打印小票功能(1).rp` 断言 Preview!="" 且 Degraded==false）；无压缩炸弹/越界风险（扫描受上传上限约束，每轮前进 ≥1 字节最坏 O(n)）。

## Docker SQLite 启动失败修复（commit 9e70eca）
- 现象：容器启动报 `failed to initialize database, got error unable to open database file: out of memory (14)`。
- 根因：镜像以 haiku(UID 10001) 运行；宿主机 bind mount 目录 `/root/haiku/data` 属主 root:root 755。SQLite(WAL) 需在**目录**里创建 `haiku.db-wal/-shm`，目录不可写 → SQLITE_CANTOPEN(14)，glebarez 纯 Go 驱动误报为 "out of memory"（与内存无关）。db 文件本身 -rw-r--r-- 属 10001 可写，迷惑性来源即此。
- 修复两层：① `repository.Connect` sqlite 分支打开前用探针文件 `ensureDirWritable` 预检数据目录，不可写时报「数据目录不可写 + chown -R 10001:10001 建议」（database_test.go 两个用例锁行为，root 下跳过只读用例）；② 新增 `docker-entrypoint.sh`（postgres 镜像同款模式）：root 启动 → `chown -R haiku:haiku /app/data /app/conf` → su-exec 降权运行；`--user` 非 root 启动直接透传。Dockerfile 装 su-exec、移除 `USER haiku`、ENTRYPOINT 换入口脚本。
- 注意：`su-exec` 同时加进 fallback apk 分支；镜像内 healthcheck 用的 busybox wget 不受影响。

## Docker 部署二次报错排查：conmon failed / Failed to get working directory（非代码 bug）
- 现象：重建镜像后 `docker run` 立即报 `[conmon]: Failed to get working directory` + `Error: conmon failed: exit status 1`，容器根本未启动（与之前 sqlite 的 App 内部报错是两层不同问题）。
- 排除：server 代码无 Getwd/"working directory"；su-exec 与 conmon 主干均无该字符串 → 错误来自运行时层（conmon=podman 监控进程）。
- 根因（最可能）：shell 当前目录被删/改名（悬空 cwd）——用户把项目从 ~ 迁到 ~/ris/haiku-wiki 后，shell 仍停在已消失的旧路径，docker run 继承该死 cwd，conmon 无法 getcwd 退出。佐证：同一镜像此前能正常启动（出过 sqlite App 报错），说明镜像可起容器，是宿主环境变了。
- 解法：先 `cd` 到真实目录再重跑；`docker --version` 若显示 podman 则 conmon 术语正常。依赖运行时栈问题时用 `docker run --rm alpine echo ok` 隔离、查 `rpm -q podman conmon crun` 与 journalctl。
- 注意：要让 sqlite 修复(commit 9e70eca)生效必须重新 `docker build`（docker.io/library/haiku-wiki:latest 若是旧镜像只会回到 out of memory(14)）。

## SQLite 启动失败终极根因：配置错配（非权限）

- 代码侧（commit 947fe57）：sqlite 分支空 DSN 默认落 <DataDir>/haiku.db；DSN 含 @ / tcp( / :// 即判定为连接串，立即报「driver/DSN 不匹配」二选一指引，不再当文件 open。新增 TestConnectSQLiteConnStringDSN。
