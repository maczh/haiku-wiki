### 原始需求复述（用户原话，三项改造）

1. 无论**创建的文档**还是**上传的文档**，都生成文档 **MD5 摘要**。
2. 无论 MD5 相同的文档被上传或保存多少次，**实际文件内容只保存一份**，只是被引用在不同的文库、目录中；对应的**预览图、缩略图同样只保存一份**。上传文件校验完 MD5 发现相同后**不再执行上传动作，直接保存新的 meta 数据**，实现「**秒传**」。
3. Markdown 文档的**编辑与预览**要求支持流程图、时序图、类图、甘特图、ER 图、时间线图、饼图、思维导图等图的编辑、真实预览、保存、读取。
4. 每天**凌晨 2 点**刷新（重新导入）一次所有由**网络 URL 导入的接口文档**，并且前端提供**手动重新导入（刷新）**功能，但**不要影响接口调试历史**。

### 用户已拍板的四条设计决策（写入本文作为**硬约束**，实现不得偏离）

| # | 决策 | 含义 |
| --- | --- | --- |
| D1 | **去重范围收窄** | 正文（手写内容）**只记录 MD5 摘要**用于识别重复，**仍留在 `docs.content`**，**不搬到内容寻址存储**。只有**上传的文件原件 + 预览图 + 缩略图**搬到内容寻址存储、物理只存一份。 |
| D2 | **删除语义** | **只删 meta，物理内容一律不删**（不实现引用计数删除）。孤儿内容靠后续后台任务人工/定期清理，**本期不实现清理任务**。 |
| D3 | **自动刷新来源** | **只对本次改动之后新导入的文档生效**——URL 导入时落库来源 URL 与导入时间。历史已导入文档无法追溯刷新；**本期不做「补录来源 URL」界面**。 |
| D4 | **Mermaid 范围** | 只要求**修通渲染 + 八种图类型逐一验证**（编辑预览、阅读态、保存、读取）；**不做**编辑器工具栏的「插入图表模板」菜单。 |

## 二、产品定义

### 2.1 产品目标

| # | 目标 | 成功后用户可感知的变化 |
| --- | --- | --- |
| **G1** 一份内容只占一份空间 | 解决"同一份合同/图纸/PPT 被反复上传到多个文库，磁盘与对象存储成倍膨胀" | 重复上传**秒级完成**（无字节上传）；同一文件出现在多个目录/文库中，但物理只存一份；删除某个引用不影响其他引用 |
| **G2** Markdown 具备真实图表表达能力 | 解决"mermaid 代码块在编辑预览与阅读态都只显示成一堆原始文字"（当前因 Vditor `js/mermaid` 资源未拷贝而**静默失效**） | 在 Markdown 里写八类图的代码块，编辑时右侧预览即出图，阅读页打开即出图，保存后再打开仍是图 |
| **G3** 接口文档保持"新鲜"且历史不丢 | 解决"URL 导入的接口文档一旦导入就永久定格，上游改了接口本地不知道" | 每天早上到公司打开接口文档就是最新的；自己前一天调过的接口，调试历史（参数/响应/耗时）**原样还在** |

**可度量的成功判据（建议作为验收基线）**

- 同一文件上传 N 次，存储中该内容物理对象数 **= 1**；第 N（N≥2）次上传**服务端写盘调用次数 = 0**。
- 秒传命中时，浏览器网络面板**无文件字节上传**（请求体 < 10 KB）。
- 八种 mermaid 图类型 × 2 个场景（编辑预览 / 阅读态）= **16 个渲染用例全部出图**，控制台**无 mermaid 资源 404**。
- 刷新前后，`api_debug_history` 中该 `doc_id` 的**行数与 `records` 内容逐字节不变**。

### 2.2 用户故事

**普通成员（内容生产者 / 消费者）**

- **US1** 作为一名普通成员，我希望**上传一份已经有人传过的文件时，不用等上传进度条**（秒传），以便快速把同一份材料放到我的文库目录里。
- **US2** 作为一名普通成员，我希望在 Markdown 里写**流程图/时序图/类图/甘特图/ER 图/时间线图/饼图/思维导图**时，**编辑预览与阅读页都能看到真正的图**，以便用图讲清技术方案而不必另存截图。
- **US3** 作为一名接口联调人员，我希望**在接口文档页面点一下就能刷新到上游最新接口**，且**我之前调过的接口历史还在**，以便不用重录调试参数。

**知识库负责人（空间与目录管理者）**

- **US4** 作为知识库负责人，我希望**同一份内容被多个目录引用时只占一份空间**，并且**删掉其中一个引用不会把别处还在用的内容弄坏**，以便我能放心做目录整理。
- **US5** 作为知识库负责人，我希望**一眼看到接口文档的"最后刷新时间/刷新状态"**，以便判断这份文档是不是已经过期、需不需要手动刷。

**管理员（平台运营）**

- **US6** 作为管理员，我希望**每天 02:00 的自动刷新任务是可观测的**（跑没跑、成功几个、失败几个、失败原因），以便出问题时能定位而不是"静悄悄失败"。
- **US7** 作为管理员，我希望**明确知道"去重后同一份内容的 URL 会被多个知识库共享、且 `/uploads/*` 是免鉴权路径"这一风险**，并已接受或已采取缓解措施，以便不出现"跨库内容被 URL 猜到"的合规事故。

## 三、需求池

> 优先级定义：**P0 = 必须有**（不做则本次交付不成立）；**P1 = 应该有**（显著提升可用性）；**P2 = 可以有**（本期可不做）。

### 3.0 全局硬约束（所有需求共同遵守）

- **C1 正文不去重**：`docs.content` 保持现状存储正文，**禁止**把正文搬入内容寻址存储（D1）。
- **C2 只删 meta**：删除文档/附件**不得**删除任何物理对象；**禁止**实现引用计数删除（D2）。
- **C3 兼容底线**：Git 仓库现状中 **零 hash 逻辑**、`storage` 包**无任何 hash 元数据能力**、`docs` 表**无独立文件表**（文件信息塞在 `docs.content` 的 JSON 里）。改造必须**向后兼容历史数据**：历史 `/uploads/...` URL 必须继续可访问，历史文档无需改写。
- **C4 迁移必须成对**：新增/改动的模型除了改 `repository/database.go` 的 `AutoMigrate`，**必须**同步 `service/migrate_service.go` 的 `migrateTables`，否则 DB 迁移时**静默丢表**。
- **C5 单实例假设**：定时任务可用进程内 ticker 实现（项目目前**完全没有** cron/scheduler 基建、`r.Run()` 阻塞、无优雅退出、无分布式锁）。**本期不引入分布式调度**。
- **C6 刷新不得重建文档**：刷新接口文档**必须就地更新 content**，**绝不重建文档、绝不改变接口的 `id`**——`api_debug_history` 靠 `endpoint_id` 锚定，改 id 即历史全失联。这是本次改造的**最高优先级兼容底线**。

### P0（必须有）

#### P0-1 每篇文档都有 MD5 摘要

| 项 | 内容 |
| --- | --- |
| 需求 | 所有文档（**手写类 + 上传类**）在落库/保存时生成并持久化 MD5 摘要；手写类正文的摘要存在 `docs` 的**新列**（建议 `content_md5`，`CHAR(32)` + 索引），上传类文档的摘要等于其**原件 MD5**（与附件记录一致）。 |
| 验收 | ① 新建一篇 Markdown，写入固定文本后保存：DB 中该行摘要 = 该文本（规范化换行后）的 MD5，可用 `md5sum` 复算一致。<br>② 编辑正文后保存，摘要随之变化。<br>③ 上传一份 `a.pdf`：该文档行的摘要 = `a.pdf` 文件本身的 MD5，与 `md5sum a.pdf` 一致。<br>④ 历史存量文档不回填也不阻塞（摘要为空的文档不参与重复提示，见 P1-1）。 |

#### P0-2 上传文件「秒传」——命中即跳过上传动作，只写 meta

| 项 | 内容 |
| --- | --- |
| 需求 | 上传链路上先算 MD5 → 命中已存在内容则**不写盘、不新增物理对象**，直接复用已有存储路径，仅新增一条 meta 记录（新 doc 行 + 新 attachment 行）。前端在提交前做一次**预检**：命中则完全不发送文件字节。 |
| 验收 | ① 同一文件连续上传 2 次：第 2 次 **存储新增对象数 = 0**，服务端无 `Put` 写盘调用；两次返回的**可访问 URL 完全一致**。<br>② 第 2 次请求体 **< 10 KB**（浏览器 Network 面板核对），无 `multipart/form-data` 文件段。<br>③ `attachments` 表该 MD5 下有 **2 行 meta**（上传者/文件名各不同），但 `storage_path` 相同。<br>④ 秒传命中的文件在阅读页可正常预览/下载（证明 URL 复用有效）。<br>⑤ 上传一个**同 MD5 但扩展名不同**的文件：按"内容相同"处理（复用同一物理对象），meta 中记录各自原始文件名与 MIME。 |

#### P0-3 原件 / 预览图 / 缩略图 三者都内容寻址去重

| 项 | 内容 |
| --- | --- |
| 需求 | 派生资源（CAD 图纸的 `svg`/`png` 派生、图片的 `preview.jpg`/`thumb.jpg`/`original.jpg`）与原件一样**只存一份**：派生写入前必须先判定"是否已存在"（键存在或 MD5 命中），已存在则**跳过写入并复用既有 URL**。 |
| 验收 | ① 同一份 CAD 图纸重复导入 2 次：派生目录中**新增派生对象数 = 0**，两次返回的 `derived.svg` / `derived.png` URL 一致。<br>② 同一张图片（无独立文档、仅上传）重复上传 2 次：`preview`/`thumb`/`original` 三个对象均**只存在 1 份**。<br>③ 派生失败（无转换器）时不产生 0 字节空文件（沿用现有 degraded 降级语义）。 |

#### P0-4 同一份内容可被多个知识库 / 目录引用

| 项 | 内容 |
| --- | --- |
| 需求 | 一份物理内容允许被 N 个文档引用；文档可位于不同文库、不同目录、不同用户。引用关系**不落引用计数**（D2），仅表现为"多条 meta 行指向同一 storage_path"。 |
| 验收 | ① 同一文件上传到**两个不同知识库**：得到 2 个 doc 行、2 个 attachment 行，`storage_path` 相同；两处均可正常预览与下载。<br>② 同一文件上传到**同一知识库的两个不同目录**：同上。<br>③ **删除其中一处引用**（进回收站或彻底删除 meta）后，另一处的文件**仍可正常访问**（物理对象未被删）。<br>④ 切换存储（local↔S3）后，引用关系与 URL 语义不自相矛盾（沿用现有 `KeyFromURL`/`URLFromKey` 约定）。 |

#### P0-5 重复内容的呈现与提示

| 项 | 内容 |
| --- | --- |
| 需求 | 用户上传已知文件时，必须**明确告知发生了什么**，避免误以为"上传失败"或"文件被替换"。 |
| 验收 | ① 秒传命中：前端提示「**检测到相同内容，已秒传（仅新增引用，未重复存储）**」并展示 MD5 前 8 位与文件大小。<br>② 非命中（新内容）：沿用现有正常上传提示，无额外弹窗。<br>③ 手写文档保存时若检出与另一篇文档摘要相同：给出**非阻断**提示（不阻止保存、不自动合并）。<br>④ 提示文案不泄露其他用户/其他知识库的文件名与路径（仅展示 MD5 与大小）。 |

#### P0-6 Markdown 内八类 Mermaid 图渲染打通（编辑预览 + 阅读态）

| 项 | 内容 |
| --- | --- |
| 需求 | 修通 mermaid 资源链路，使 Markdown 代码块中 `flowchart` / `sequenceDiagram` / `classDiagram` / `gantt` / `erDiagram` / `timeline` / `pie` / `mindmap` 八种图在**编辑实时预览**与**阅读态**都渲染为图形，且**保存—读取往返不破坏原代码块**。 |
| 现状 | （已核实）构建脚本 `web/scripts/copy-vditor-assets.mjs` 的 `INCLUDE` 白名单**缺 `js/mermaid`** → Vditor 内部请求 `/vditor/dist/js/mermaid/mermaid.min.js` 得 404 → **代码块原样显示、无任何报错（静默失效）**。 |
| 验收 | ① 八种图类型逐个用例：编辑态右侧预览**出 SVG 图形**（非代码文本）；阅读态打开同一文档同样出图。**共 16 个用例全过**。<br>② 浏览器控制台**无 mermaid 相关 404/加载失败**；断网（禁外网）环境下同样渲染成功（自托管要求）。<br>③ 保存—刷新—重新打开：正文中代码块**原文一字不差**（图不被转成 HTML 固化、不被转义破坏）。<br>④ 版本快照/导出（PDF、HTML）中图形正常呈现（至少 PDF/HTML 导出不出现裸代码块）。<br>⑤ 与既有独立的 `flowchart` doc_type（npm `mermaid ^11.17.2`）和 `mindmap` doc_type（`simple-mind-map`）**互不干扰**——Markdown 代码块与它们是两套东西。 |
| 明确不做 | 编辑器工具栏的「插入图表模板」菜单（D4）。 |

#### P0-7 每日 02:00 自动刷新 URL 导入的接口文档

| 项 | 内容 |
| --- | --- |
| 需求 | 建立**进程内定时调度**（每日本地 02:00 触发），对所有「**通过 URL 导入且已落库来源 URL**」的 `doc_type=api` 文档，重新拉取并重新解析，**就地更新正文**。导入时必须落库**来源 URL** 与**导入时间**（当前只存了一个 `import_source` 分组名字符串，无来源 URL、无导入时间，需补）。 |
| 生效范围 | **仅本次改动之后新导入的文档**（D3）。历史文档因无来源 URL **不参与刷新**，也不提供补录界面。 |
| 验收 | ① 新导入一份接口文档后，该文档 meta 中可见**来源 URL** 与**导入时间**，且**重启服务后仍在**（持久化，非内存）。<br>② 定时任务触发（可用可控时间入口验证，例如把触发时间临时配置成 1 分钟后）后：上游新增一个接口 → 刷新后文档正文出现该接口；`updated_at` 变化；来源 URL 与首次导入时间**保留不变**。<br>③ 一次刷新覆盖**全部**符合条件的文档；单个文档失败不影响其他文档继续刷新。<br>④ 上游接口被删除时按 P0-10 的策略处理，且**不产生异常崩溃/无限重试**。<br>⑤ 任务只在**单实例**下运行，重复启动不产生并发刷新同一文档（进程内互斥即可）。 |

#### P0-8 前端手动「刷新」入口

| 项 | 内容 |
| --- | --- |
| 需求 | 接口文档页面（编辑态与阅读态）提供**手动刷新（重新导入）**按钮，走与自动刷新**完全相同的刷新逻辑**，避免两套代码路径行为不一致。 |
| 验收 | ① 编辑态与阅读态均可触发刷新；**无来源 URL 的文档按钮置灰并给出原因提示**（"该文档非 URL 导入，无法刷新"）。<br>② 刷新中按钮 loading、**防重复点击**；刷新结束给出明确结果提示（成功 N 个接口 / 无变化 / 失败原因）。<br>③ 手动刷新与自动刷新对同一文档的处理结果**逐字段一致**（幂等：连续刷新 2 次，第 2 次结果与第 1 次相同，不产生重复分组或重复接口）。 |

#### P0-9 刷新**不得影响接口调试历史**（最高优先级兼容底线）

| 项 | 内容 |
| --- | --- |
| 需求 | 刷新为**就地更新正文**：不删除/重建文档行，不改变接口的 `id`。同一来源新拉取的接口，若 `method + uri` 与旧接口一致，**必须沿用旧 `id`**。 |
| 验收 | ① 刷新前后，`api_debug_history` 中该 `doc_id` 的**行数不变**、`records` JSON **逐字节不变**（DB 前后 diff 为空）。<br>② 刷新后打开某个刷新前调过的接口的「调试历史」抽屉，**仍能看到刷新前的全部历史记录**（含参数、响应、耗时）。<br>③ 刷新后该接口的 `id` 与刷新前**完全相同**（可用 DB 或前端断言核对）。<br>④ 刷新导致接口被移除时，其历史记录**仍保留在库中**（不级联删除）。 |

#### P0-10 刷新失败 / 来源不可达时的行为

| 项 | 内容 |
| --- | --- |
| 需求 | 刷新失败**绝不破坏已有内容**，且必须留下可诊断的痕迹（状态 + 原因 + 时间）。 |
| 验收 | ① 来源不可达/超时/返回非接口文档格式时：文档正文**保持刷新前内容**（浏览器回读对比一致）。<br>② 该文档被标记为**刷新失败**并记录：**最后刷新时间**、**状态（成功/失败）**、**失败原因**（可读文案，如"连接超时"/"返回内容非 Swagger/OpenAPI/Postman 格式"）。<br>③ 前端可见失败状态与原因（见四、UI 要点 ③）。<br>④ 单文档连续失败**不产生重试风暴**（每天到点只尝试一次），下一次到点正常重试。<br>⑤ 刷新成功后失败状态与原因被清除。 |

### P1（应该有）

#### P1-1 手写正文重复提示（只提示，不合并）
保存手写文档时若检出**另一篇**文档摘要相同，非阻断提示「内容与《X》相同」。验收：提示出现但保存成功；不同文档可同时存在相同正文。
> 说明：正文按 D1 留在 `docs.content`，**不做合并、不做去重入库**，避免破坏版本快照与权限模型。

#### P1-2 刷新状态 / 最后刷新时间在界面可见
验收：接口文档页（或文档树悬浮信息）可见「最后刷新：YYYY-MM-DD HH:mm　状态：成功/失败」。见 UI 要点 ③。

#### P1-3 定时任务执行结果可观测（管理员）
验收：管理员可见最近一次刷新任务：**开始时间、结束时间、扫描文档数、成功数、失败数、失败文档列表（可跳转）**。单实例内存 + 落库最近一次结果即可。

#### P1-4 去重命中率只读统计
验收：可查看"总上传次数 / 命中秒传次数 / 节省字节数"（只读指标，**不参与删除决策**，不引入引用计数语义）。

## 四、UI 设计稿要点

> 文字描述 + ASCII 草图即可，不需要出图。交互统一沿用 Ant Design 5（`message`/`notification`/`Tag`/`Tooltip`）。

### ① 重复文件上传时的提示（秒传命中）

- 触发点：上传/导入弹窗提交后、服务端预检返回命中。
- 形态：**轻量提示（toast）**，不弹模态框（模态框会让"秒传"反而显得像报错）。上传条目就地变为已完成的成功态，进度条**直接跳到 100%**（或显示"秒传"标签）。
- 文案：`检测到相同内容，已秒传 —— 仅新增引用，未重复存储（MD5 ab12cd34 · 2.4 MB）`
- 附件列表中的区分：秒传项带一个 `Tag`（`秒传`，蓝色）与 Tooltip「该文件内容已存在于文库中，本次仅新增引用」。

### ② 接口文档手动「刷新」按钮位置与结果反馈

- 位置：**接口文档顶栏（`ApiEditor` 顶栏右侧操作区）**，紧邻已有的「导入」按钮，与「保存」同一组 `Space`。**阅读态同样可见**（阅读态已复用 `ApiEditor` 并开启 `readOnly`，刷新属于内容维护动作，阅读态也应允许发起——按 P0-8 要求，阅读态保留「刷新」、隐藏「保存/导入」）。
- 图标/文案：复用现有 `ReloadOutlined` 图标 + 文案「刷新」；紧邻位置展示**最后刷新时间**（见 ③）。
- 可点性：无来源 URL 时按钮 `disabled`，Tooltip「该文档非 URL 导入，无法刷新」。
- 结果反馈（toast，三态）：
  - 成功：`刷新成功：新增 2 个接口，更新 5 个接口，移除 0 个` + 「查看」链接（定位到变更分组）。
  - 无变化：`刷新成功：内容无变化（来源未更新）`。
  - 失败：`刷新失败：连接超时（已保留原内容）` —— **必须带"已保留原内容"字样**，消除用户对数据丢失的恐慌。

## 五、待确认问题（需用户拍板，附推荐选项与理由）

| # | 问题 | 推荐选项 | 理由 |
| --- | --- | --- | --- |
| **Q1** | 去重后**同一份内容的 URL 会被多个知识库共享**，而 `/uploads/*` 是**免鉴权静态路径**。是否可接受？ | **可接受，但必须做两点缓解**：① **存储键名不得使用纯 MD5**（见 Q2）；② 秒传/预检响应**不返回**其他用户的文件名、路径、所属知识库。 | 现状已免鉴权（`r.Static("/uploads", ...)` / `S3` 走 `StorageProxy`），本次改造**不新增**泄露面（同一份内容本来就是同一条 URL）。但"共享"放大了影响半径，故建议不加鉴权（避免破坏历史 URL 与 `<img>` 直链），而是**收紧键名可猜性 + 收紧响应信息**。若用户要求"必须鉴权"，则应作为**独立安全需求**单独排期（会破坏历史 `/uploads/...` 直链与导出 HTML 的图片加载）。 |
| **Q2** | CAS 的**键名是否直接用 MD5**？ | **不要纯 MD5 键名**。建议键名 = `uploads/cas/<md5 前 2 位>/<md5>-<随机 6 位>.<ext>`，**去重靠 DB 的 md5 索引**而不是靠键名。 | 纯 MD5 键名 = 任何人只要拿到一份文件（如公司公开文档）就能算出 URL，从而**枚举猜出他人上传的同一内容**；在免鉴权 `/uploads` 下等于"内容可被反查"。用 md5 只做**索引**同样满足"物理只存一份"，且不牺牲不可枚举性。**若用户坚持纯内容寻址键名，则 Q1 必须升级为"`/uploads` 改鉴权 + 签名 URL"**，二者不可同时保留现状。 |
| **Q3** | 手写正文摘要相同时，是否要**合并/去重入库**？ | **只提示，不合并**（D1 已定：正文留在 `docs.content`）。 | 正文合并会牵连版本快照、协作者、权限、目录结构，收益（省几百 KB 文本）远小于风险。 |
| **Q4** | "秒传预检"接口的权限边界：命中时是否直接写 meta？ | **预检只回"是否命中"**；写 meta 仍走**原有上传/新建接口的正常鉴权**（用户必须对自己要落文档的文库有写权限）。 | 否则用户可借秒传把任意内容"引用"到自己无权写入的文库，形成越权写入。 |
| **Q5** | 刷新时**上游已删除的接口**如何处理？ | **保留本地接口、标记为 stale（"上游已移除"）**，不自动删除。 | 本地可能有补充说明、示例、已联调过的记录；自动删除会让用户措手不及且失去历史。若用户希望"严格对齐上游"，可加一个「刷新后同步删除」开关，默认关闭。 |
| **Q6** | 是否支持**手动上传文件（非 URL）的接口文档参与自动刷新**？ | **不支持**，只有**记录到来源 URL** 的导入才刷新（D3）。 | 本地文件没有可重新拉取的来源；历史文档不做补录界面（D3）。 |
| **Q7** | 02:00 的**时区**基准？ | **Asia/Shanghai（服务器本地时区，容器内需显式设置 `TZ`）**。 | 面向国内企业用户，"凌晨 2 点"按用户本地时间才有意义；用 UTC 会变成上午 10 点刷新。 |
| **Q8** | 自动刷新任务**是否需要落库执行记录**（还是内存足够）？ | **落库"最近一次结果"**（P1-3），不建完整任务历史表。 | 单实例 + 无调度基建，落库最近一次即可满足"可观测"；建全量任务表属于过度设计。 |
| **Q9** | 秒传预检需要**前端计算大文件 MD5**（可能几十 MB～百 MB），是否接受短暂等待？ | **接受**，但要求用 **Web Worker + 分片读取 + 进度提示**，且设一个文件大小阈值（建议 ≥ 20 MB 才走"先算 hash 再上传"的策略；小于阈值直接上传，由服务端算 hash 并在响应里返回"已秒传"标记）。 | 避免"为了省几十 KB 上传，先让用户等 3 秒算 hash"的体验倒挂；阈值策略能让小文件走最简单的路径。 |
| **Q10** | 本次改造是否要求**存量历史文件也享受秒传**（即回填 MD5）？ | **不要求**（P2-1 离线脚本可选）。 | 回填需遍历全量存储并读全部文件、在单实例上跑，成本高且与"历史 URL 不改写"的目标无关；不做只影响"历史文件再次上传时无法秒传"这一小场景。 |

## 六、给架构师的落点提示（事实约束，非设计方案）

> 仅为避免设计走偏，供架构阶段参考；最终设计以架构师方案为准。

1. **唯一原件落盘入口**：`server/internal/service/upload_service.go` 的 `saveBytes`（键名规则 `uploads/YYYY/MM/<uuid>.<ext>`，随机名）。**MD5 计算与命中判定应在此收敛**，避免多路径各自为政。
2. **派生图入口**：`attachment_service.go` 的 `saveDerivedFile`（同目录、同基名、换扩展）——需在此加"已存在则跳过写入"。图片派生（`preview.jpg`/`thumb.jpg`/`original.jpg`）来自 `imgconv.Convert`，其产物经上传链路落盘，同样需覆盖。
3. **storage 包**目前只有 `Put/Read/Open/Delete/Exists/List/URL/LocalPath`，**无 hash 元数据能力**——MD5 需落在**业务层/DB**，不建议改 storage 接口（会牵动 S3 与迁移逻辑）。
4. **文件信息全在 `docs.content` 的 JSON 里**，**没有独立文件表**；`attachments` 表是唯一可挂 MD5 的地方，建议加 `md5`（`CHAR(32)` + 索引）。
5. **接口文档 URL 导入 100% 在前端**（`web/src/lib/apiDoc.ts` + `web/src/components/editor/ApiEditor.tsx` 的 `mergeImported`，经 `PATCH /api/docs/:id` 落库）；后端**没有**对应 handler。→ 落库**来源 URL + 导入时间**需要改**前后端两侧**；建立**服务端刷新能力**是新工作（后端要去 fetch 上游并解析 Swagger/OpenAPI/Apifox/Postman）。
6. **`mergeImported` 现有逻辑**：按 `import_source` **先删旧分组再全量重导**——这正是会**重建接口 id** 的写法，是实现 P0-9 的**最大风险点**，刷新必须走"按 `method + uri` 保留旧 id"的合并策略，而非整体替换。
7. **构建侧**：修 P0-6 的最小改动是往 `web/scripts/copy-vditor-assets.mjs` 的 `INCLUDE` 加入 `js/mermaid`（同时确认 Vditor 内 mermaid 版本与本项目 `mermaid ^11.17.2` 的能力差异，八种图类型需逐一验证是否被该版本支持）。
8. **迁移成对**：新增 `attachments.md5`、`docs.content_md5` 等列/模型时，需同步 `repository/database.go` 与 `service/migrate_service.go` 的 `migrateTables`（C4）。
